## 先回答一个问题：能不能交给官方代做

不能，也没有这个入口。三条理由：

1. 平台手册里只有「从 Git 仓库导入项目」，没有代创建服务。
2. 参赛协议要求作品为大赛期间新开发、本人原创。「平台使用深度」20 分明确靠**开发过程截图和对话记录**核验，交给别人做等于这 20 分直接归零。
3. 反过来，这也意味着**一轮 prompt 出成品是最差打法**。要故意拆成多轮，每轮有可见改动，截图留证。

可以借力的地方是：先把素材仓库推到 Gitee，用「平台添加项目」导入，省掉一个个传文件的麻烦。但开发必须发生在平台对话里。

## 前置动作：素材怎么进平台

`04-平台素材/platform_assets.zip`（478 KB，远低于 10 MB 上限）里已经打包好全部真实资产：

| 包内文件 | 用途 |
| --- | --- |
| `demo_images/` + `manifest.json` | 18 张真实钢材缺陷照片（六类各 3 张），含中文名与真实置信度 |
| `platform_data.json` | 聚合摘要：KPI、分布、月度趋势、闭环对比、6 个归因样例、30 条抽样记录 |
| `knowledge_base.json` | 30 条冶金规则，含触发条件、建议、预期降幅 |
| `attribution_engine.py` | 归因引擎参考实现，零第三方依赖 |
| `records.json` | 1200 条带 ground truth 的检测记录 |

两条路，选一条：

- **主路**：新建任务，把 `platform_assets.zip` 作为附件上传，第一轮提示词里说明「解压到项目根目录」。
- **备路**：若对话框不支持上传，把 `04-平台素材` 整个目录推到 Gitee 仓库，用「平台添加项目」导入，第一个需求填「基于项目里的素材开发应用」。

模型权重 `01-数据/model/onnx/best_fp16.zip`（5.61 MB）**第二轮再传**，第一轮先不碰，避免沙箱装不上推理引擎拖慢主线。

## 第一轮 · 搭骨架 + 检测工作台（今天必须跑起来）

```text
请开发一个名为「钢材质量缺陷归因与闭环处置平台」的 Web 应用，面向制造业质检「只检不诊」的痛点。
我已上传 platform_assets.zip，请先解压到项目根目录，里面是本项目要用的真实素材，后续模块都要基于它们实现。

本轮先实现骨架和检测工作台，其余模块预留导航位但不要写死残缺页面。

1. 顶部导航：检测工作台 / 归因诊断 / 知识库 / 整改工单 / 闭环验证 / 分析看板。

2. 页面顶部常驻四项指标卡（数字固定，来自离线评测，不是实时计算）：
   缺陷识别准确率 94.44%、根因定位准确率 94.68%、改进建议可执行率 100%、闭环缺陷率降幅 25.64%。
   每张卡下方用小字标注口径，例如「NEU-DET 测试集 170/180」。

3. 检测工作台（左右两栏）：
   左侧：上传图片，或点击「载入示例样件」按钮。示例样件读 demo_images/manifest.json，
   按六类分组展示，点击任一缩略图即加载对应的真实钢材缺陷照片。
   六类固定为：龟裂 crazing、夹杂 inclusion、斑块 patches、麻点 pitted_surface、
   氧化皮压入 rolled-in_scale、划痕 scratches。
   右侧：识别结果，含缺陷类别、置信度、严重等级（按置信度折算，分 轻微/中等/严重）。

4. 检测接口做成双通道，独立成一个函数 detect(image_path)，按此优先级：
   通道 A：尝试 import onnxruntime，若可用则加载 model/best_fp16.onnx 做真实推理（输入 224×224，
   输出取置信度最高的类别）。我会稍后上传这个模型文件。
   通道 B：若 onnxruntime 不可用或模型文件不存在，则读 demo_images/manifest.json 中该图的
   confidence 字段作为返回结果。这是离线评测得到的真实置信度，不是编造值。
   返回结果里必须带一个 mode 字段标明走的是哪个通道，页面上用一行小字显示
   「实时推理」或「离线评测结果」。两个通道都不能返回随机值。

5. 检测记录表：每次检测写入 SQLite，含时间、图片名、缺陷类型、置信度、严重等级、推理通道。
   初始化时从 records.json 导入前 200 条作为历史记录展示。

龟裂类的三张样例置信度只有 0.5 左右，明显低于其他类，这是模型真实短板。
在龟裂结果卡片上加一行灰色小字说明「此类缺陷纹理细密，识别难度最高」，不要隐藏这个事实。
```

## 第二轮 · 工艺上下文 + 证据链归因引擎

```text
检测工作台已可用，现在实现归因诊断模块。这是本应用的核心。

1. 工艺上下文表单（检测工作台右侧，带默认值，支持一键载入典型场景）：
   设备参数：轧制温度(℃)、轧制速度(m/s)、张力(kN)、除鳞水压力(MPa)、辊缝(mm)、压下率(%)

   候选根因列表：除主因外的其他命中项，按贡献度排列
   缺失字段要显式列出，说明哪些维度因数据不足未参与计算

   参考 platform_data.json 里的 attribution_demos，那是 6 个完整样例，前端可直接拿来做样式对齐和空态填充。
```

## 第三轮 · 知识库 + 建议可执行率 + 整改工单

```text
补充知识库、建议生成、整改工单三部分。

1. 知识库：直接从 knowledge_base.json 导入 30 条规则，字段为
   「缺陷类型 - 根因 - 触发条件 - 解决策略 - 预期降幅(%)」。
   支持新增、编辑、删除、启停，卡片列表展示，可按缺陷类型筛选。
   不要自己补充或改写规则内容，那 30 条是整理好的行业规则。

2. 改进建议生成：归因完成后从知识库匹配解决策略，原样输出 solution 字段，
   不要改写、不要概括。每条建议标注「预期降低缺陷率 X%」，取自 expected_drop_pct。
   页面上必须显示建议的完整原文，例如「除鳞水压力由 12.5MPa 提升至 ≥18MPa」这种带具体参数的表述。

3. 建议可执行率统计卡片（重要，这是赛题考核指标之一）：
   每生成一条建议就判定一次，需同时满足三个条件才算可执行：
   含具体数值、含量化依据（物理量纲或 ≥ ≤ 区间或可数单位）、不含空泛口号词（加强、重视、意识、责任心）。
   页面上显示：已生成 N 条建议，可执行 M 条，占比 X%，并给出判定条件的说明。
   当前 30 条规则全部满足，占比应为 100%，请把这个数字真实展示出来。

4. 整改工单：归因 + 建议合成工单，字段含工单号、关联检测记录、主因、建议措施、责任人、状态。
   状态流转：待处理 → 处理中 → 已解决 → 已关闭。列表支持按状态和根因维度筛选。

5. 自然语言问答：归因页做问答入口，用户可追问「为什么会出现划痕」。
   调用对话里的 AI 模型回答，回答时必须带上本次归因的证据链作为上下文，
   要求结论落在知识库规则范围内，不确定的部分明确说不确定。
```

## 第四轮 · 闭环验证（差异化核心）

```text
这是整个应用最重要的模块，请重点实现。闭环验证指：执行整改建议后重新抽检，验证缺陷率是否真的下降。

1. 流程：工单「执行整改」后进入闭环验证页，选择批次，输入复检样本量（默认 200），点击「执行复检」。
   整改后缺陷率 = 整改前缺陷率 × (1 - 各条已执行建议预期降幅的累乘)。
   只统计归因正确的件，归因错误的件不产生改善。

2. 展示：
   整改前后缺陷率对比卡（大数字 + 降幅百分比 + 判定结果）
   前后对比柱状图
   连续 8 个批次缺陷率趋势折线，标注整改发生的时间点
   按缺陷类型的整改前后分项对比表

3. 判定阈值：降幅 ≥20% 判定为「闭环有效」（绿色），≥30% 判定为「效果显著」（深绿），
   低于 20% 判定为「效果不显著」（橙色）。不要用 30% 作为唯一达标线，
   在保守假设下本数据集整体降幅为 25.64%（39.17% → 29.12%），按 20% 判定才符合实际。

4. 真实性标注：页面显著位置必须写明
   「闭环验证为基于规则库预期降幅参数的工况推演，用于演示闭环逻辑，不代表真实产线效果」。
   并在旁边说明：接入真实产线后，把预期降幅换成实测复检数据，同一套代码即可输出真实对比。
   不许隐瞒这是仿真。
```

## 演示数据要求（贯穿全程）

- 检测记录 ≥1000 条，覆盖 3 个钢种（Q235B / SS400 / SPHC）、6 类缺陷

- 生成脚本开放给评委查看，页面标注数据为模拟生成
