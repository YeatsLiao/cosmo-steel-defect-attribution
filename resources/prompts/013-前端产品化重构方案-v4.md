## 一、问题诊断（实测 + 截图实证）

测试环境：本地 `127.0.0.1:8123`，无头 Chrome 1440×900，七页截图存于 `_shots_v4/v4_<页面>.png`。

### 1.1 操作入口收敛

| 位置 | 现状 | 判定 |
|------|------|------|
| 顶栏 | 问号按钮 + 常驻气泡「第一次用？30 秒上手 →」 | 气泡是 demo 味最重的一处，且遮挡内容 |
| 帮助抽屉 | 内含「新手导览」按钮，抽屉本身也是帮助入口 | 入口套入口 |
| 首页 | `home-source` 整张卡片只放一句数据声明 + 「数据来源」按钮 | 一整张卡承载一行字，属信息浪费 |
| 页脚 | 版权行末尾又挂一个「数据来源」按钮 | 与首页卡、抽屉重复 |
| 检测工作台 | 左栏「上传图片」+「载入样件」，右栏空态卡内第三个「载入样件」 | 同一动作三个入口，主次不分 |
| 全站 | 四个指标胶囊条在六个非首页页面常驻，且全部跳同一处看板 | 六个页面各占 36px，不值 |

帮助类入口合计 **5 个可点元素 + 1 个抽屉**，`index.html` 中相关引用 20 处。

### 1.2 首页

实测现状：hero 108px 只放标题 + 34 字副标题，两端留白；「核心指标」卡为 2×2 数字格，卡片底部约 120px 空白（卡片被同行「作业流程」撑高，内容撑不满）；「作业流程」是与首页定位无关的第五条导航；「最新告警」与「数据来源」各占一卡。全页**无任何图片**，首屏只能靠文字推销自己。

### 1.3 流程进度与并发

| 问题 | 证据 |
|------|------|
| 进度是摆设 | 侧栏只有一个 `进度 0 / 5` 文本 + 导航项右上角 8px 小圆点；页面内无进度表达 |
| 进度会被"访问"污染 | `loadDashboard()` 里 `setFlow("dashboard", true)` —— 进一次看板就算一步完成 |
| 语义不清 | `detectSample` 一次请求同时置 `sample` 与 `detect` 两步；`flowDone` 与真实数据无校验，刷新后仅靠 localStorage |
| 无并发控制 | 全文件搜 `AbortController` / `signal` / `token` 零命中。连点「开始归因」会并发两个请求，后返回者覆盖先返回者；`runAttribution` 的 `finally` 无条件 `setBtnLoading(btn,false)`，还会把新请求的按钮状态提前复位 |
| 无重复触发处理 | 归因执行中改缺陷类型或换场景，无人拦截；复检执行中改批次会再发一次请求（`cl-batch` 的 change 里直接 `runVerify`） |
| 无取消能力 | 归因/复检/识别三类长任务全都没有取消入口 |

### 1.4 术语与闭环说明

界面上「整改工单」「闭环验证」只有名字，没有任何业务定义：谁提出、何时触发、输入输出是什么、谁负责，都查不到。闭环页给一个降幅数字，但不解释它是怎么构成的。这直接导致两个后果：

1. 用户实测遇到的困惑——「工单点完已完成，再去闭环验证到底验证什么」；
2. **口径冲突**：单类整改推演出来是 4.81%（效果不显著），而全站宣传的指标是 25.64%。两者都对，但页面上没有任何一句话把「本次只整改了 1 类，六类全做完才是 25.64%」讲清楚，评审当场就会问住。

后端其实已经把需要的字段都返回了（`per_class` 里含 `expected_drop` / `attribution_acc` / `effective_drop` / `executed`，`measures` 里含代表措施与预期降幅），只是前端没把它们组织成"修复项 → 指标变化"的对应关系。

### 1.5 平铺 Tab

| 页面 | 现状 | 问题 |
|------|------|------|
| 归因诊断 | 结果区 3 个平铺 Tab（主因与证据 / 改进建议 / 智能问答） | **动线断在 Tab 上**：唯一能把结论转成工单的按钮在第二个 Tab 里，用户看完主因不知道下一步在哪 |
| 闭环验证 | 2 个 Tab（复检推演 / 历史） | 历史是次要留痕，却与主流程平级占一行 |
| 知识库 | 无 Tab，30 条规则卡片平铺 + 分页 12/页，仅有缺陷类型下拉 | 30 条规则一眼看不出结构，没有按维度/预警条件的分组与检索 |
| 整改工单 | 无 Tab，2 个筛选下拉（状态 / 维度） | 状态筛选与卡片上的状态轨道重复，且轨道本身不可点 |

### 1.6 UI/UX 一致性

`style_guide.md` 定义了规范，但落地有几处偏离：卡片内边距 12/14px 两套值；空态有 `.empty`、`.guide-card`、`.cl-empty-state` 三种写法，文案结构不统一；`index.html` 里还有内联 `style="margin-top:12px"` 十余处；模块标题、页标题字号层级在不同页不完全一致；工单页筛选标签里的三条横线图标（`M3 6h18 / M6 12h12 / M9 18h6`）语义不明，像禁用图标。

## 四、交互状态设计

### 4.1 统一任务状态机

识别 / 归因 / 复检推演三类长任务，共用一套状态与表现：

| 状态 | 主按钮 | 页面表现 | 可打断性 |
|------|--------|---------|---------|
| 空闲 | 可点，文案为动作（开始归因） | 正常 | — |
| 执行中 | 禁用 + 内联转圈，文案不变（归因中…） | 目标区骨架屏；任务条显示 `归因中… 1.2s` + 「取消」 | 可取消 |
| 完成 | 恢复可点 | 结果回填 + 任务条停留 2s 显示 `归因完成 608ms` → 淡出 | — |
| 失败 | 文案不变，结果区给「重试」 | 错误态：错误文案 + 重试按钮 | — |

### 4.2 并发与重复触发规则

| 场景 | 规则 |
|------|------|
| 同一任务的第二次触发 | 按钮已禁用，点击无效；前端不排队（避免假进度） |
| 检测：连点不同样件 | 新请求 abort 旧请求，只渲染最新一次结果；缩略图高亮以最后一次点击为准 |
| 归因：执行中改参数/换场景 | 不自动重跑。参数区可继续编辑，主按钮保持禁用并提示「归因中…」；完成后如需按新参数计算，由用户再点一次 |
| 归因：已启动诊断 A 又点诊断 B | 不允许并行。B 的触发被拦截在按钮层；若 A 正在执行，提供「取消本次」→ 取消后按钮立即恢复，用户可再点 B |
| 复检：执行中改批次/样本量 | 拦截。批次与样本量控件在执行中置为只读，避免"看起来换了批次其实还是旧结果" |
| 跨页切换 | 任务不中断（状态存模块级），回到该页自动回填结果；任务条跟随到当前页顶部显示 |
| 失效回调 | 每个任务持 `runToken` 与 `AbortController`；`await fetch` 后先校验 token，不匹配直接 return，绝不覆盖新结果；`finally` 只在 token 仍存活时复位按钮 |

### 4.3 进度显著化

进度不再由"访问过哪个页面"决定，改由**真实数据**判定：

| 步骤 | done 判定依据 |
|------|--------------|
| ① 载入样件 | 存在 `currentSample`（识别结果已回填） |
| ② 识别缺陷 | 最近一次识别成功（`available === true`） |
| ③ 定位根因 | `lastAttrResult` 存在且无 `error` |
| ④ 生成工单 | `/api/work-orders` 非空，且至少一张状态非「待处理」 |
| ⑤ 复检验证 | `/api/closed-loop/runs` 有记录 |

首次加载时用接口回填（工单、复检记录各请求一次），刷新后进度不丢也不虚高。左栏进度卡显示：五个节点时间线（当前节点高亮可点）+ `已完成 N / 5` + 「下一步：<动作> →」主按钮。

### 4.4 统一状态反馈规范

| 类型 | 规范 |
|------|------|
| 加载 | 列表/卡片用骨架屏；按钮用内联转圈；禁止全屏遮罩 |
| 空态 | 统一三段：结论句（暂无工单）+ 一句说明（归因后点生成整改工单）+ 一个动作（去归因诊断 →）。不再出现纯文字空卡 |
| 错误 | 统一 `错误文案 + 重试按钮`，所有接口失败都走同一组件 |
| 禁用 | 明确原因提示（如「工单未完成」徽标），不出现无解释的灰按钮 |
| 危险操作 | 删除规则改模态二次确认（当前用原生 confirm） |
| 成功反馈 | 顶部 toast，2.5s 自动消失；关键结果同时落到页面状态里，不只靠 toast |

### 4.5 窄屏（<1100px）

左栏收起为顶部横向步骤条；卡片内边距降为 12px；能力三卡改单列；归因页左参数列折叠为一行摘要条；看板图表单列堆叠；全站不出现横向滚动条。

## 五、术语与口径文案（写入帮助中心「术语与口径」段）

**整改工单**
把一条归因结论转成可派发、可跟踪的整改任务。
何时产生：在归因诊断页点「生成整改工单」。
输入：主因根因、缺陷类型、整改措施、责任人、关联检测记录。
输出：工单号与状态（待处理 → 处理中 → 已完成 → 已关闭）。
谁负责：质量工程师出结论，班组长或工艺员执行整改。

**闭环验证**
整改做完后重新抽检一批样件，看缺陷率到底降没降。
触发条件：至少一张工单进入「已完成」。
输入：复检批次、样本量、纳入验证的整改项。
输出：复检前缺陷率、复检后缺陷率、降幅、判定（效果显著 / 闭环有效 / 效果不显著）。
谁负责：质量主管判定是否放行，未达标退回继续整改。

**缺陷率是怎么降下来的**
1. 归因给出主因与整改措施，措施带一个「预期降幅」（来自知识库规则的量化经验值）。
2. 措施被执行、工单推进到「已完成」，该措施才有资格计入复检降幅。未完成的工单在闭环页灰置，标注「未计入」。
3. 复检时，对每一类缺陷：有效降幅 = 预期降幅 × 该类归因正确率。只算归因正确的件——归因错误的件整改了也不会变好，这一步扣掉的是"改错方向"的损耗。
4. 复检后缺陷率 = 复检前缺陷率 − Σ各类有效降幅折算的百分点。逐项对应关系在闭环页「降幅构成」表里可直接核对。
5. **为什么单类整改只有 4.81%，全站却写 25.64%**：前者只整改了 1 类缺陷，后者是六类全部按标准方案整改完成的基准值。闭环页口径说明会一并展示这两个数字，避免误读。

**指标口径**（合并进帮助中心，含真实性声明）
缺陷识别准确率 94.44%（NEU-DET 测试集 170/180）；根因定位准确率 94.68%（离线评测集，基线 92.13%）；改进建议可执行率 100%（30 条规则全覆盖）；闭环缺陷率降幅 25.64%（39.17% → 29.12%，工况推演）。缺陷图片来自公开 NEU-DET 数据集，工艺参数与闭环推演为模拟数据，检测支持实时 ONNX 推理与离线评测双通道。
